# Когда не работает

Всё описанное ниже **случалось на живой системе** 2026-09-05/06 — это не
список гипотез. Начинать всегда с `ocbar doctor`: он проверяет компоненты
по отдельности и обычно называет причину сам.

---

## Вход

### Окно логина открывается снова и снова, код не подходит

Скорее всего, супервизор работает по старой копии кода. Долгоживущий
процесс на bash держит функции в памяти, и правка файла его не меняет.

```bash
ocbar doctor                 # строка «Супервизор» скажет, свежий ли код
ocbar supervisor restart     # принудительно
```

С 2026-09-06 супервизор следит за своим файлом и перезапускается сам, а
`doctor` предупреждает, если процесс старше кода. Если видите такое —
значит запущена версия старше этой.

### Второй фактор вводится неверно

Проверьте, тот ли секрет:

```bash
ocbar secret status          # покажет источник и текущий код
```

Сравните код с приложением. Не совпал — источник не тот. Частая причина:
в экспорте Google Authenticator **несколько записей**, и раньше импорт молча
брал первую. Смотрите, что внутри, и выбирайте явно:

```bash
ocbar secret import-qr <файл> --list
ocbar secret import-qr <файл> --select <часть имени>
```

Код подставляется **один раз за вход**: несколько неверных подряд блокируют
учётную запись. Если фактор уже заблокирован, `ocbar` тут не поможет —
разблокировка на стороне провайдера входа.

### Форма не заполняется, окно ждёт человека

Так и задумано: на нераспознанной форме `ocbar` ничего не нажимает. В логе
будет строка с перечнем видимых полей:

```
форма не распознана, поля: text:smsCode
```

Если поле должно заполняться — сначала посмотрите, какие правила действуют
и откуда они взяты:

```bash
ocbar rules show <профиль>     # «inline» — секция [Autofill] профиля, «file:…» — файл, «builtin» — встроенные
```

Править нужно тот источник, который назван, иначе правка ни на что не
повлияет (D49):

- **профиль-файл** (`~/.config/ocbar/profiles/<имя>.ocbar`) — правила в его
  секции `[Autofill]`. Проще всего разметить форму заново: `ocbar learn
  <профиль>` или «Разметить портал…» в редакторе профиля; руками — там же,
  текстом. Готовый файл правил кладётся в профиль командой
  `ocbar rules import <файл> <профиль>`, секция убирается
  `ocbar rules clear <профиль>`;
- **файл `autofill.rules`** читается, только если в профиле нет секции
  `[Autofill]`: тогда берётся файл из ключа `Rules` в `[Auth]`, а без ключа —
  общий `~/.config/ocbar/autofill.rules`, если он есть. У старого формата
  (`profiles.conf`) — ключ `rules` или тот же общий файл.

Проверить, что получилось, — JS автозаполнения по файлу правил:

```bash
"$(brew --prefix ocbar)/libexec/ocbar-auth" --dump-script --rules ~/.config/ocbar/autofill.rules
```

Правила из `[Autofill]` при каждом входе кладутся во временный файл
`~/Library/Application Support/ocbar/rules/<профиль>.rules` — его можно
подать в `--rules` так же. Правила читаются при каждом запуске,
пересобирать ничего не нужно.

> **UPD 2026-09-10:** раньше здесь советовалось править только
> `~/.config/ocbar/autofill.rules`. При заполненной секции `[Autofill]` в
> профиле этот файл не читается (D49).

### Вход прошёл, но туннель не поднялся: `401 Unauthorized`

```
Got inappropriate HTTP CONNECT response: HTTP/1.1 401 Unauthorized
Cookie was rejected by server; exiting.
```

Балансировщик увёл вход на конкретный узел, и сессия принадлежит **ему**.
Подключаться надо туда же, а не на общее имя. Исправлено 2026-09-06: в логе
теперь видно строку «балансировщик увёл на …». Если её нет — версия старая.

### `Server certificate verify failed: signer not found`

Это не ошибка, а сообщение перед проверкой по отпечатку. Сертификат шлюза
выдан внутренним центром, и `openconnect` сверяет его с хешем, полученным в
ответе шлюза (`--servercert`). Если следом идёт `Connected to HTTPS` —
всё в порядке.

## Туннель и сеть

### Туннель умер после действий с launchd

```bash
launchctl bootout gui/$(id -u)/ru.ocbar.supervisor
```

раньше убивал и туннель: `openconnect` оставался в задаче агента, а launchd
завершает всё дерево. Исправлено — теперь он запускается в своей сессии.
Проверить версию хелпера:

```bash
/usr/local/libexec/ocbar-helper version    # сравните с версией в libexec/ репозитория
sudo ocbar install                          # обновить
```

### Внутренние адреса не резолвятся

```bash
ocbar dns status                       # что в /etc/resolver и как это видит система
dscacheutil -q host -a name <имя>
dig +short @<резолвер из tunnel.env> <имя>
```

Если `dig` напрямую отвечает, а система нет — зоны не применены: посмотрите
`ocbar status`. Если не отвечает и `dig` — проблема на стороне резолвера или
нет маршрута до него.

Зона со значением `vpn` требует поднятого туннеля: адрес берётся из того,
что прислал шлюз. Без туннеля такая зона пропускается.

### Трафик не идёт в туннель

```bash
ocbar status                     # маршруты подсвечены: через utun, мимо, выключены
netstat -rn -f inet | grep utun
```

Сеть могла быть выключена переключателем в меню — вернуть:

```bash
ocbar routes add 10.0.0.0/8
```

Помните: `ocbar` ставит **только** сети из `networks.conf`, список шлюза
намеренно игнорируется. Если нужной сети нет — допишите её в конфиг.

### Домашняя сеть или лаборатория пропали при включении VPN

Значит подключение идёт чужим клиентом либо в `networks.conf` (или в
`[Routes]` профиля) есть сеть, которая накрывает домашнюю, — например
`0.0.0.0/1` и `128.0.0.0/1` для «всего в туннель». `ocbar` ставит только
перечисленные сети: **[проверено]** при поднятом туннеле адреса
`192.168.х` продолжали ходить своим путём, хотя шлюз просил забрать всю
`192.168.0.0/16`.

> **UPD 2026-09-10:** раньше здесь упоминался режим `full` — он убран
> (D4, D32), профиль с `mode = full` не загружается.

### После падения остались зоны, маршруты или чужой DNS

```bash
ocbar doctor       # перечислит мусор
ocbar cleanup      # уберёт только своё
```

Чужие файлы в `/etc/resolver` не трогаются никогда: удаляется лишь то, что
записано в собственном манифесте.

## Пауза

### `pause` говорит, что хелпер старее CLI

```bash
sudo ocbar install
```

Хелпер живёт в root-каталоге и обновляется только установкой, поэтому легко
отстаёт от остального.

### После паузы маршруты вернулись сами

Такого быть не должно: супервизор знает про паузу и не восстанавливает
маршруты, а реконнект её не отменяет. Если это происходит — проверьте, что
и хелпер, и CLI свежие (`ocbar doctor`, строка «Версия хелпера»).

## Установка

### `install: … and … are the same file`

Установщик брал источником уже установленный хелпер. Исправлено; если
видите — обновите репозиторий и повторите.

### `Bootstrap failed: 5: Input/output error`

Агент выгружался и загружался подряд. Теперь установщик не трогает
работающий агент вовсе — новый код супервизор подхватывает сам. Если агент
не загружен:

```bash
ocbar supervisor start
```

### `brew audit` ломает сам Homebrew

**[проверено 2026-09-05]** `brew audit` доустанавливает гем `json`, который
конфликтует со встроенным в portable-ruby, после чего **любая** команда brew
падает с `undefined method 'default_sort_keys_proc='`. Лечится удалением
того, что audit создал:

```bash
rm -rf "$(brew --repository)/Library/Homebrew/vendor/bundle/ruby/"*/gems/json-*
rm -rf "$(brew --repository)/Library/Homebrew/vendor/bundle/ruby/"*/extensions
```

Это баг Homebrew, а не формулы. Саму формулу проверяйте сборкой из
локального tap.

## Настройки, о которых редко вспоминают

Всё перечисленное — переменные окружения; они нужны в основном для проверки
и для нестандартных случаев.

| Переменная | Что делает |
|---|---|
| `OCBAR_VERBOSE=1` | подробный лог входа в поток ошибок |
| `OCBAR_SHOW=1` | показать окно входа сразу |
| `OCBAR_CONFIG_DIR` | другой каталог конфигурации целиком |
| `OCBAR_CONFIG`, `OCBAR_NETWORKS` | отдельные файлы зон и сетей |
| `OCBAR_STATE_DIR`, `OCBAR_USER_STATE` | каталоги состояния (для прогонов на тестовых данных). `OCBAR_STATE_DIR` — только вместе с `--dry-run`: sudo её не пропускает, и CLI при заданной переменной хелпер от root не зовёт |
| `OCBAR_AUTH`, `OCBAR_BIN` | пути к аутентификатору и к самой программе (для плагина меню) |
| `OCBAR_NOTIFY=0` | выключить уведомления, не трогая конфигурацию |
| `OCBAR_LOG_MAX` | порог ротации логов в байтах |
| `OCBAR_LOG_DIR` | другой каталог журналов (самопроверка пишет во временный) |
| `OCBAR_RECONNECT_GRACE` | сколько ждать самостоятельного восстановления связи |
| `OCBAR_RECONNECT_TIMEOUT` | сколько openconnect пытается восстановиться сам |
| `OCBAR_LOGINS_PER_HOUR` | предохранитель: сколько полных входов в час разрешено |
| `KP_DB`, `KP_CLI` | путь к базе паролей и к её утилите |

Ещё есть режим конечного числа циклов супервизора — `ocbar supervise
--iterations=N`. Он удобен, чтобы посмотреть на решения супервизора, не
оставляя его работать.

## Меню-бар

### Переключатель сети или зоны возвращается назад

Было до 2026-09-07 у профилей одним файлом (`.ocbar`): `routes` и `dns`
не загружали профиль, смотрели в старый `networks.conf`, ничего там не
находили — и отметка «выключено» не сохранялась. На живом туннеле маршрут
снимался, но возвращался при переподключении.

```bash
ocbar selftest       # «сеть выключается» — эта проверка ловит именно такое
```

Со старым форматом (`profiles.conf` + `networks.conf`) всё работало, поэтому
и не всплывало раньше.

### Действия из меню ничего не делают

Хелпер стоит без `NOPASSWD`: `sudo` спрашивает пароль, а терминала у меню
нет. С 2026-09-07 меню говорит об этом прямо, но проверить можно и так:

```bash
ocbar doctor                 # строка «sudoers»
sudo ocbar install           # чинит навсегда
```

### Приложение зовёт не тот `ocbar`

Первая строка журнала приложения называет, какой файл найден:

```bash
head -1 ~/Library/Logs/ocbar/app.log
```

Так уже случалось: бандл, собранный в репозитории, звал `ocbar` из tap —
то есть отстающий код. Путь можно задать явно переменной `OCBAR_BIN`; если
она указывает в пустоту, приложение это скажет, а не возьмёт молча другой.

### Выбрал другой профиль — ничего не произошло

До 2026-09-08 `ocbar connect <другой>` при поднятом туннеле отвечал «уже
подключён» с кодом 0, и меню молчало. Теперь это переключение: вход в новый
профиль, потом отключение старого и подключение — в журнале супервизора
строка «смена профиля». Меню перед этим спрашивает подтверждение: смена
стоит нового входа со вторым фактором.

### Прокси-режим: «порт уже занят» или «нет ocproxy»

```bash
ocbar doctor                 # раздел «Прокси-режим»: есть ли ocproxy, свободен ли порт
brew install ocproxy
networksetup -getsocksfirewallproxy Wi-Fi   # включён ли на сервисе чужой SOCKS (настройка системы)
lsof -nP -iTCP:<порт> -sTCP:LISTEN          # какой процесс занял порт
```

`networksetup` показывает только настройку сетевого сервиса — какой SOCKS
система раздаёт программам; кто слушает порт, он не знает. Занятый порт —
это `lsof`.

Порт настраивается в профиле (`[Proxy] Port`). `10808` на этой машине занят
сторонним SOCKS — редактор так и скажет.

### Прокси-режим: «системный SOCKS не включён»

Хелпер отказался ставить наш SOCKS, потому что на сервисе уже включён чужой
(на этой машине — `127.0.0.1:10808`). Это не ошибка подключения: прокси
работает, программы с явным `--socks5-hostname` ходят. Чужую настройку
клиент не перезаписывает (D40) — либо выключить её самому, либо снять
`SystemProxy` в профиле. После `brew upgrade` та же строка может значить,
что хелпер отстал: `sudo ocbar install`.

### Вход остановился: «поле … пустое, заполнить нечем»

С 2026-09-10 движок не жмёт кнопку, пока на странице видно пустое поле из
правил (D53): иначе форма ушла бы с пустым паролем. Причины две. Либо нечем
заполнить — пароль вводит человек, его нет в хранилище, код уже потрачен;
либо правило `fill` находит на странице лишнее поле.

```bash
ocbar secret status <профиль>     # есть ли пароль и код
ocbar rules show <профиль>        # какие правила действуют
ocbar learn --probe <профиль>     # что видно на первом окне
```

### `ocbar profiles` ничего не печатает, `connect` молча выходит

Было до 0.2.10: при двух и больше профилях-файлах и без `default = …` в
`profiles.conf` оба молча завершались (D56). Обновитесь или укажите
профиль явно: `ocbar connect <профиль>`.

### Код из связки не подходит, а в приложении на телефоне — подходит

Скорее всего, у записи нестандартные параметры: SHA256 или SHA512, 8 цифр,
период не 30 с. До 0.2.10 они терялись, и ocbar считал код как SHA1, 6 цифр,
30 с (D56). Посмотреть, что записано, и занести заново:

```bash
ocbar secret status <профиль>          # «из Keychain … (SHA256, 8 цифр, 60 с)»
ocbar secret import-qr <файл> <профиль>   # параметры лягут в профиль сами
```

Код по счётчику (HOTP) ocbar не ведёт: счётчик живёт в приложении, и две
копии разойдутся после первого же входа.

### «Камерой…» пишет, что доступ к камере запрещён

Разрешение macOS спрашивает от имени приложения, которое запустило ocbar:
вход из меню — `ocbar.app`, из терминала — сам терминал. Включить:
Системные настройки → Конфиденциальность и безопасность → Камера. До 0.2.9 у
`ocbar.app` не было строки о камере, и процесс завершался без вопроса (D55):
обновитесь, `brew upgrade ocbar`.

### Камера не находит QR

Поднесите телефон ближе, чтобы QR целиком был в кадре, прибавьте яркость
экрана. Экспорт на несколько страниц листайте — камера остановится на
нужной записи сама. «Ни одна не даёт ваш код» значит, что на экране не та
учётка: выберите в экспорте VPN.

### Окно «Запомнить для следующего входа?» не появилось

Оно появляется, только если галочка «Запомнить, как я вхожу» была включена,
окно входа видел человек и хоть одна форма отправлена. Если вход прошёл сам,
спрашивать нечего. На старом формате профиля (`profiles.conf`) галочки нет:
правила некуда положить — переведите профиль в файл, `ocbar export`.

### Секрет TOTP «не даёт введённый вами код»

Окно сохранения принимает секрет, только если он даёт код, который вы
только что ввели. Не совпало — значит, секрет от другой записи или другой
учётки. Из экспорта Google Authenticator с несколькими записями нужная
находится сама — по тому же коду.

### Пароль с кириллицей не подставлялся

Было до 2026-09-10: `security -w` отдаёт не-ASCII пароль шестнадцатеричной
строкой без признаков, и ocbar подставлял эти цифры. Теперь чтение через
`-g` (D54). Если пароль заводили раньше — он в связке верный, чинить нечего.

### Разметка ничего не предзаполнила

Предзаполнение отмечает только надёжное (D52): стандартный `autocomplete`,
единственное поле пароля, логин перед ним, поле кода по имени, кнопку формы
по умолчанию. Если портал рисует поля без формы или полей пароля два —
отмечать руками. Посмотреть, что узнаётся, можно без окна:

```bash
ocbar learn --probe <профиль>     # первое окно портала; ничего не нажимает
```

### Кнопка «Разметить портал…» серая

Было до 0.2.4: редактор считал любой открытый профиль «несохранённым» —
обработчики полей срабатывали на саму загрузку профиля, — а разметка при
несохранённых правках блокировалась. Сильнее всего это било после выбора
другого профиля в списке. Теперь правки определяются сравнением с файлом на
диске, а при настоящих правках кнопка сначала сохраняет профиль и потом
открывает форму. Серой она остаётся только без имени файла, при ошибках в
профиле (они внизу окна) или пока идёт разметка.

```bash
ocbar-app --selftest        # строки «редактор: …» открывают редактор на настоящем окне
```

### Уведомления приходят от «Script Editor» или не приходят вовсе

С 2026-09-09 уведомления шлёт приложение меню-бара (D50). Если они всё ещё
от «Script Editor» — приложение не запущено (`ocbar app status`), клиент
показывает их сам, запасным путём. Если не приходят совсем — система ждёт
разрешения: «Системные настройки → Уведомления → ocbar → Разрешить»; в
журнале приложения при запуске строка «уведомления: разрешены / не
разрешены».

> **UPD 2026-09-10:** приложение принимает `ocbar://notify` только со своим
> одноразовым токеном: при запуске кладёт его в
> `~/Library/Application Support/ocbar/notify.token` (права 0600), рядом —
> `notify.allowed` («1», если уведомления разрешены). Клиент идёт через
> приложение, только если оно запущено, в `notify.allowed` стоит «1» и токен
> читается; иначе — запасной путь от «Script Editor». Значит, «Script Editor»
> теперь означает ещё и «уведомления ocbar не разрешены» (D59).
>
> **UPD 2026-09-10 (0.3.1):** от «Script Editor» уведомлений больше не
> бывает вовсе (D61). Приложение не запущено — клиент запускает его сам.
> Уведомления запрещены — не приходит ничего, а в меню ocbar появляется
> строка «Уведомления выключены — Разрешить…»; непоказанные уведомления
> видны в `~/Library/Logs/ocbar/supervisor.log` строкой «уведомление не
> показано».

### Подключается без окна, а нужно войти с нуля

Окно входа помнит сессию провайдера входа, поэтому после `ocbar disconnect`
следующий вход часто проходит без формы — так задумано. Для проверок входа с
нуля: `ocbar logout` — отключение и сброс сессий окна входа (пароль и секрет
кода в связке остаются). В меню то же — строка «Выйти совсем (сброс входа)»,
она видна после `ocbar app devmode on` (D68).

### Клавиша ⌥⌘P не работает

Сочетание занято другой программой. Тогда подсказка в меню не показывается,
а в журнале приложения при запуске написано «не досталась». Пауза остаётся
доступной из меню.

## Диагностика: куда смотреть

| Что | Где |
|---|---|
| решения супервизора, реконнекты, события сна | `~/Library/Logs/ocbar/supervisor.log` |
| что окно входа заполнило и почему нет (хосты цепочки, окна формы, кнопки «Вставить») | `~/Library/Logs/ocbar/auth.log` |
| вывод openconnect | `/var/db/ocbar/openconnect.log` |
| что сказал шлюз при подключении | `/var/db/ocbar/tunnel.env` |
| наши зоны, маршруты, системный SOCKS | `/var/db/ocbar/{zones,routes,socks}.state` |
| подробности входа | `OCBAR_VERBOSE=1 ocbar connect --show` |
| что шлюз предлагает, без учётных данных | `"$(brew --prefix ocbar)/libexec/ocbar-auth" --probe --url <host>/<group>` |

> **UPD 2026-09-10:** с хелпера 0.8.0 состояние — в `/var/db/ocbar`. Раньше
> оно лежало в `/usr/local/var/ocbar`, а этот каталог на Intel принадлежит
> пользователю (D57). Переносит `sudo ocbar install`; до него файлы лежат по
> старому пути, и CLI читает их оттуда. `ocbar doctor` показывает, какой
> каталог действует.
