# Когда не работает

Всё описанное ниже **случалось на живой системе** 2026-09-05/06 — это не
список гипотез. Начинать всегда с `ocbar doctor`: он проверяет компоненты
по отдельности и обычно называет причину сам.

---

## Вход

### Окно логина открывается снова и снова, код не подходит

Скорее всего, супервизор работает по старой копии кода. Долгоживущий
процесс на bash держит функции в памяти, и правка файла его не меняет.

```bash
ocbar supervisor status      # сравните время запуска с датой правки
ocbar supervisor restart
```

С 2026-09-06 супервизор следит за своим файлом и перезапускается сам, а
`doctor` предупреждает, если процесс старше кода. Если видите такое —
значит запущена версия старше этой.

### Второй фактор вводится неверно

Проверьте, тот ли секрет:

```bash
ocbar secret status          # покажет источник и текущий код
```

Сравните код с приложением. Не совпал — источник не тот. Частая причина:
в экспорте Google Authenticator **несколько записей**, и раньше импорт молча
брал первую. Смотрите, что внутри, и выбирайте явно:

```bash
ocbar secret import-qr <файл> --list
ocbar secret import-qr <файл> --select <часть имени>
```

Код подставляется **один раз за вход**: несколько неверных подряд блокируют
учётную запись. Если фактор уже заблокирован, `ocbar` тут не поможет —
разблокировка на стороне провайдера входа.

### Форма не заполняется, окно ждёт человека

Так и задумано: на нераспознанной форме `ocbar` ничего не нажимает. В логе
будет строка с перечнем видимых полей:

```
форма не распознана, поля: text:smsCode
```

Если поле должно заполняться — добавьте правило в
`~/.config/ocbar/autofill.rules` и проверьте, что получилось:

```bash
ocbar-auth --dump-script --rules ~/.config/ocbar/autofill.rules
```

Правила читаются при каждом запуске, пересобирать ничего не нужно.

### Вход прошёл, но туннель не поднялся: `401 Unauthorized`

```
Got inappropriate HTTP CONNECT response: HTTP/1.1 401 Unauthorized
Cookie was rejected by server; exiting.
```

Балансировщик увёл вход на конкретный узел, и сессия принадлежит **ему**.
Подключаться надо туда же, а не на общее имя. Исправлено 2026-09-06: в логе
теперь видно строку «балансировщик увёл на …». Если её нет — версия старая.

### `Server certificate verify failed: signer not found`

Это не ошибка, а сообщение перед проверкой по отпечатку. Сертификат шлюза
выдан внутренним центром, и `openconnect` сверяет его с хешем, полученным в
ответе шлюза (`--servercert`). Если следом идёт `Connected to HTTPS` —
всё в порядке.

## Туннель и сеть

### Туннель умер после действий с launchd

```bash
launchctl bootout gui/$(id -u)/ru.ocbar.supervisor
```

раньше убивал и туннель: `openconnect` оставался в задаче агента, а launchd
завершает всё дерево. Исправлено — теперь он запускается в своей сессии.
Проверить версию хелпера:

```bash
/usr/local/libexec/ocbar-helper version    # нужна 0.3.0 или новее
sudo ocbar install                          # обновить
```

### Внутренние адреса не резолвятся

```bash
ocbar dns status                       # что в /etc/resolver и как это видит система
dscacheutil -q host -a name <имя>
dig +short @<резолвер из tunnel.env> <имя>
```

Если `dig` напрямую отвечает, а система нет — зоны не применены: посмотрите
`ocbar status`. Если не отвечает и `dig` — проблема на стороне резолвера или
нет маршрута до него.

Зона со значением `vpn` требует поднятого туннеля: адрес берётся из того,
что прислал шлюз. Без туннеля такая зона пропускается.

### Трафик не идёт в туннель

```bash
ocbar status                     # маршруты подсвечены: через utun, мимо, выключены
netstat -rn -f inet | grep utun
```

Сеть могла быть выключена переключателем в меню — вернуть:

```bash
ocbar routes add 10.0.0.0/8
```

Помните: `ocbar` ставит **только** сети из `networks.conf`, список шлюза
намеренно игнорируется. Если нужной сети нет — допишите её в конфиг.

### Домашняя сеть или лаборатория пропали при включении VPN

Значит подключение идёт в режиме `full` либо чужим клиентом. В режиме
`split` этого не бывает: **[проверено]** при поднятом туннеле адреса
`192.168.х` продолжали ходить своим путём, хотя шлюз просил забрать всю
`192.168.0.0/16`.

### После падения остались зоны, маршруты или чужой DNS

```bash
ocbar doctor       # перечислит мусор
ocbar cleanup      # уберёт только своё
```

Чужие файлы в `/etc/resolver` не трогаются никогда: удаляется лишь то, что
записано в собственном манифесте.

## Пауза

### `pause` говорит, что хелпер старее CLI

```bash
sudo ocbar install
```

Хелпер живёт в root-каталоге и обновляется только установкой, поэтому легко
отстаёт от остального.

### После паузы маршруты вернулись сами

Такого быть не должно: супервизор знает про паузу и не восстанавливает
маршруты, а реконнект её не отменяет. Если это происходит — проверьте, что
и хелпер, и CLI свежие (`ocbar doctor`, строка «Версия хелпера»).

## Установка

### `install: … and … are the same file`

Установщик брал источником уже установленный хелпер. Исправлено; если
видите — обновите репозиторий и повторите.

### `Bootstrap failed: 5: Input/output error`

Агент выгружался и загружался подряд. Теперь установщик не трогает
работающий агент вовсе — новый код супервизор подхватывает сам. Если агент
не загружен:

```bash
ocbar supervisor start
```

### `brew audit` ломает сам Homebrew

**[проверено 2026-09-05]** `brew audit` доустанавливает гем `json`, который
конфликтует со встроенным в portable-ruby, после чего **любая** команда brew
падает с `undefined method 'default_sort_keys_proc='`. Лечится удалением
того, что audit создал:

```bash
rm -rf "$(brew --repository)/Library/Homebrew/vendor/bundle/ruby/"*/gems/json-*
rm -rf "$(brew --repository)/Library/Homebrew/vendor/bundle/ruby/"*/extensions
```

Это баг Homebrew, а не формулы. Саму формулу проверяйте сборкой из
локального tap.

## Диагностика: куда смотреть

| Что | Где |
|---|---|
| решения супервизора, реконнекты, события сна | `~/Library/Logs/ocbar/supervisor.log` |
| вывод openconnect | `/usr/local/var/ocbar/openconnect.log` |
| что сказал шлюз при подключении | `/usr/local/var/ocbar/tunnel.env` |
| наши зоны и маршруты | `/usr/local/var/ocbar/{zones,routes}.state` |
| подробности входа | `OCBAR_VERBOSE=1 ocbar connect --show` |
| что шлюз предлагает, без учётных данных | `ocbar-auth --probe --url <host>/<group>` |
